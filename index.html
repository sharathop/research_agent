Composio toolkit-research take-home — agent-run diligence across CRM, support, comms & ad platforms

CRM tools hand out keys freely. Support tools vary wildly. Most agent errors were infrastructure artifacts.

An agent researched 32 of the assignment's 100 apps end-to-end — auth, credential access, API surface, MCP availability, and buildability verdicts, backed by evidence URLs — before a free-tier token ceiling stopped the batch mid-run. This page details what it found, what it got wrong, and where a human post-mortem uncovered a 33% error rate on spot checks.

The agent

A Python pipeline built on Composio's SDK — one long-lived session, a fixed tool-call pattern, two models with different jobs, and a verification pass that re-checks itself before handing a verdict to a human.

  • Where a human was needed — the errors. All 7 failed apps (Aircall, Copper, Discord, Freshdesk, Front, Help Scout, Telegram) are flagged needs_human_review and would need a manual research pass. 5 were a rate-limit-driven fallback model breaking its own JSON output; 1 (Copper) was the model calling a disabled browser tool; 1 (Front) was a genuine 413 request-too-large against the per-minute token cap.
  • Where a human was needed — the "unknown" gaps. 8 completed apps came back with mcp: unknown rather than a guess (GoHighLevel, Gorgias, Lark, LiveAgent, Pumble, Slack, Twenty, Zoho Cliq). That's the agent correctly declining to invent an answer — but it means a human still has to close those out before the toolkit backlog can be prioritized.
  • Where a human was needed — sign-off on the two highest-stakes claims. The verification section below shows the automated check itself needed a manual spot check: it caught one real first-pass mistake and manufactured one false one. Composio's own diligence process should keep a human in the loop on credential_access and api.mcp specifically, not just on failures.

The verification

Every app's credential_access and api.mcp claim gets a second, independent pass: a fresh web search, then a separately-prompted model that sees only the claim and the new evidence — not the original reasoning — and returns confirmed, contradicted, or inconclusive.

The honest version: generate_final_report() retries once if the model's JSON doesn't parse — verify_report() doesn't. So 58% of checks silently died to a formatting hiccup in the small verifier call, and the "confidence downgraded from high to medium" shown for 16 of the 25 completed apps is that bug, not new evidence. Only the 11 checks that actually ran are real signal. The fix is a five-line change: give the verifier the same retry-on-parse-failure the report generator already has.

Of the checks that did run, two produced a real contradiction of the first pass. Both were spot-checked by hand against live documentation — one confirms the pipeline caught a genuine mistake, the other shows the pipeline can be wrong about being right.

Verifier: correct catch

Google Ads — the agent said no MCP server exists. It was wrong.

First pass claimed api.mcp: no. The verification search surfaced Google's own developer-toolkit page for a Google Ads MCP server and flagged the contradiction. Manual check against developers.google.com/google-ads/api/docs/developer-toolkit/mcp-server and the googleads/google-ads-mcp GitHub repo confirms it: Google ships an official, read-only MCP server (three tools — search, get_resource_metadata, list_accessible_customers). The agent's first pass missed a resource that exists; the verifier's contradiction was the correct call.

Verifier: false positive

Slack — the agent said credentials are self-serve. The verifier disagreed. The agent was right.

First pass claimed credential_access: self_serve. The verifier's search returned Slack's help article on requesting a free trial of a paid workspace plan, which does require emailing support — and used that to mark the claim contradicted, dropping confidence to low. But that evidence answers a different question: upgrading a workspace's billing plan, not getting developer API credentials. Manual check against docs.slack.dev/authentication confirms any developer can register a Slack app and generate OAuth tokens with no sales contact at all — the original self-serve claim was correct. The verifier retrieved real evidence; it just answered the wrong question with it.

Net read: the verification loop is a real improvement in concept — it caught one genuine mistake on the sample it actually reached — but this run shows two things worth fixing before trusting it at scale: a code bug capped its real coverage at 28% of completed apps, and even a "confirmed/contradicted" verdict from it still needs a human spot check, because scope-mismatched evidence can produce a confident wrong answer just as easily as a right one.

Limits, honestly & why 32 and not 100

The impact of Groq free-tier constraints and architectural bottlenecks.

  • Free-tier Groq math, not a design choice. The loop model's instrumentation showed roughly 17,500 tokens consumed per app across a 4-step tool-calling loop. Groq's free tier caps models at 8,000 tokens/minute and 200,000 tokens/day org-wide. Twenty apps alone (350k tokens) exceeded that daily ceiling, causing the batch to hit limits mid-run and rotate through fallback chains before manual intervention at 32 apps.
  • 5 of 7 errors trace to that same ceiling. When the loop fell back to smaller safeguard models, tool-call JSON malformed on 5 apps (Aircall, Discord, Freshdesk, Help Scout, Telegram), resulting in an output_parse_failed error from Groq. 1 more (Front) hit a hard 413 token-rate limit. Only 1 (Copper, invoking a disabled browser tool) was a genuine model-behavior bug.
  • What changes on Groq's Developer tier. TPM limits jump from 8k to 250k per model (~31x increase), comfortably clearing all 100 apps without rotations.
  • Category blind spots. Only 4 of 10 categories were touched; Ecommerce, Data/SEO, Infra, Finance, and AI/Research have zero data here.

Confirmed

Salesforce — Self-serve credentials and MCP verified

First pass claimed credential_access: self_serve and api.mcp: yes. Manual review confirms a free Developer Edition account combined with a self-service Connected App provides working OAuth client access without sales interaction. Furthermore, official documentation confirms Hosted MCP Servers are available for Enterprise tiers.

Contradicted (Search Collision)

Pylon — The agent conflated two companies

First pass claimed credential_access: contact_sales, citing getpylon.com/developers. That URL belongs to an Australian solar-industry CRM built by Saru Technologies—an entirely different entity from usepylon.com, the customer-support platform. The correct Pylon docs indicate self-serve bearer token generation via dashboard admin roles. This search-collision failure is a critical class of error that could recur across other generic app names.

Contradicted (Schema Conflation)

Twilio — Credential acquisition vs. Usage pricing

First pass claimed credential_access: paid. Twilio's trial and pricing documentation indicates that account creation requires no credit card and grants immediate full API access with trial credits. Costs apply strictly to post-trial usage metering, revealing that the schema blurred billing models with credential-gating rules.

Defensible / Imprecise

Twenty & Gorgias — Underselling community MCP ecosystems

Twenty was marked api.mcp: unknown because it lacks a first-party server, though at least four active community-built MCP wrappers exist. Gorgias was similarly marked unknown while third-party proxy integrations exist via Composio and Zapier. "Unknown" is safe, but toolkit builders benefit from knowing community paths exist.
